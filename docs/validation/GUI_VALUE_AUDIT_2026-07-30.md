# ExecLocus GUI・製品価値監査（2026-07-30）

## 結論

ExecLocusの中心価値は、WindowsとWSLで「実際にどの実行ファイルが選ばれるか」を同じ形式で観測し、違いの影響、確認コマンド、再診断までを短時間で示すことです。

一般的なシステム情報表示だけでは、WSL2利用者が継続して使う理由になりません。次の問いに答えられることを合格条件とします。

1. 今いるのはWindowsかWSLか。
2. Git・Node・npm・Codex・Claude Codeは、どちら側の何が選ばれるか。
3. Windows側とWSL側で、意図しない違いがあるか。
4. その違いで何が起こり得るか。
5. 次に何を確認し、直した後にどう再検証するか。

## 実利用評価による判定

Windowsアプリとして一通り操作した後も、「このツールの良さが分からない」「WSL2開発時に使おうと思えない」という評価になりました。この結果は、画面説明の不足だけではなく、現在の中心価値が日常の利用動機へつながっていないことを示します。

したがって、現時点のGUIを完成版として磨き続ける判断はしません。Windows／WSL比較は診断の内部能力として残し、製品の入口を受動的な情報表示から、作業直前に事故を止める「WSL Project Preflight」へ変更する案を第一候補とします。

### 現在の価値が弱い理由

- 実行環境の情報は、問題が起きていない利用者には確認する動機がありません。
- WindowsとWSLで値が違っても、期待された差なのか事故の原因なのかを利用者が判断する必要があります。
- 診断を手動で開くタイミングがなく、日常の開発フローに入りません。
- 結果を見た後に、作業を安全に開始できる状態まで到達しません。
- 診断対象が起動ディレクトリで決まり、任意の開発プロジェクトを選ぶ操作になっていません。

### 第一候補: WSL Project Preflight

利用者がプロジェクトを選び、`npm install`、エージェント起動、ビルドなどの前に1回チェックします。画面の主結果は技術情報ではなく、次の3状態にします。

- **開始してよい**: 期待するOS層、プロジェクト配置、主要ツールが整合しています。
- **確認してから開始**: 選択未確定、共有性と性能のトレードオフなど、人の判断が必要です。
- **このまま開始しない**: Windows版NodeをWSLプロジェクトで使うなど、具体的な事故につながる不一致があります。

各状態には「このまま進むと何が起きるか」「最小の修正」「修正後の再検証」を1つずつ示します。現在の候補一覧やWindows／WSL差分は、その結論を開いて確認する証拠へ下げます。

### 仮説更新: WSL Project Workbench

利用者ヒアリングでは、診断だけでなく、プロジェクトごとにPowerShell、CMD、WSLディストリビューション、通常／管理者権限を選び直す日常負担が確認されました。Preflightを単独製品の入口にせず、正しい環境を開いて開発タスクを始めるWorkbenchの安全確認として組み込みます。

Windows Terminalや公式WSL Settingsと競合する機能は再実装しません。ExecLocusはプロジェクトの期待環境と実測結果を保持し、既存の公式機能を正しい作業ディレクトリと権限で起動します。詳細は[WSL Project Workbench 製品仮説](../research/WSL_PROJECT_WORKBENCH_2026-07-30.ja.md)に記録します。

診断価値は、正常な環境情報ではなく、隔離した失敗状態から原因と再検証まで到達できるかで確認します。詳細は[診断シナリオラボ](DIAGNOSTIC_SCENARIO_LAB_2026-07-30.ja.md)に記録します。

### 継続利用につなげる次段階

1. 任意のプロジェクトを選ぶフォルダ選択。
2. 開発開始前チェックとして、1画面1結論に変更。
3. `execlocus guard -- <command>`形式で、実行直前に危険な環境差を警告。
4. 前回の正常状態を保存し、PATHやツール更新によるドリフトを検出。
5. 「問題を発見できた」「作業開始の判断が速くなった」のどちらも得られなければ、製品仮説を再度見直す。

## 必須機能になるための優先順位

### P0: 公開前に必要

- 診断対象フォルダを利用者が明示的に選べる。
- Windows／WSLペア診断を、手作業で2回実行せず完了できる。
- 期待する使い方と実測結果の不一致を、結論として先に示す。
- 選ばれた実行ファイル、由来、形式、候補、理由を追跡できる。
- 修正候補と確認コマンドを示し、再診断で改善を確認できる。
- 共有用出力から識別情報を置換し、画面上で確認してからコピーできる。

### P1: 継続利用につながる

- 前回診断との差分を保存し、環境更新による変化を検出する。
- チームの期待値をポリシーファイルとして保存し、逸脱を警告する。
- fnm・nvm・Voltaなど、バージョン管理ツール由来の選択根拠を説明する。
- Dev Containerやコンテナ内との境界も同じモデルで比較する。
- GitHub Issueへ貼れる再現情報を、匿名化済みMarkdownで作る。

### P2: 将来検討

- カワウソの状態アニメーション。
- WSL操作用のターミナル統合。
- Ollamaによるローカル説明補助。

P2は体験向上には役立ちますが、診断精度と問題解決時間を改善するP0/P1より先には実装しません。Ollamaは同梱サイズ、モデルライセンス、端末性能、更新・脆弱性管理を別途評価します。

## Windows／WSL自動比較の価値判定

比較画面は、単に値が違うことを示すだけでは不十分です。次を満たすときに価値があると判定します。

- 同じプロジェクトを両側から観測していることが分かる。
- OS境界として当然違う項目と、事故につながる違いを区別する。
- WSL側でWindows由来のPEや `/mnt/c` 上のツールが選ばれた場合に強調する。
- PATH、alias、functionなど、選択理由を表示する。
- 修正後に同じ条件で再比較できる。

## 利用者テストの合格条件

初見のWSL2利用者が、説明者なしで次を完了できることを確認します。

1. 30秒以内に製品の役割を説明できる。
2. 自分に合う利用目的を選べる。
3. 1回の操作でWindows／WSL比較を開始できる。
4. 60秒以内に、意図しない選択があるか判断できる。
5. 表示された確認コマンドと再診断方法を理解できる。
6. 共有前に何が匿名化されるか説明できる。

「情報が見えた」ではなく、「新しい問題を発見できた」「判断時間が短くなった」「修正後の確認に再利用したい」のいずれかを得られたかを最終評価に使います。

## 安全性と費用

- 診断は読み取り専用です。
- GUIはループバックアドレスだけで待ち受けます。
- Windows／WSL比較はローカルの `wsl.exe` とExecLocusだけを使用します。
- 外部API、ホスト型AI、有料クラウド、課金ランナーを使用しません。
- WSL補助バイナリの導入は無料ですが、利用者が明示的に実行します。
- 未加工JSONや端末出力は、共有用レポートとは別物として扱います。
